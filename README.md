# Space Tracker

Space Tracker 是一个面向 Windows 的只读磁盘空间追踪工具：它不只告诉你“现在谁占空间”，还告诉你“从上次扫描到现在，谁增长了多少”。程序使用 Rust 编写，不依赖大型 TUI 或 .NET 运行时。

## 为什么需要它

传统磁盘分析器擅长生成一张静态空间地图，但清理磁盘时真正想知道的是：

> 我上次已经看过这些目录了。现在重新打开工具时，哪些目录在这段时间里明显变大，增长发生在哪里，是否值得清理、迁移或建立链接？

Space Tracker 围绕这个用户叙事设计：

1. 第一次扫描目标目录并保存快照。
2. 之后再次扫描同一个目录。
3. 把“当前占用”和“增长占用”分成两个视图。
4. 对增长目录继续下钻到子目录和新增文件。
5. 忽略长期稳定的 Windows 和程序安装目录，把注意力放在更可能可处理的用户数据、缓存和开发产物上。

## 特性

- 无参数启动：简单的交互式 CMD 向导。
- 扫描过程中动态显示耗时、文件数、目录数、累计大小、联接点和错误数。
- 交互模式默认扫描 `C:\`，默认把数据放在 exe 所在目录。
- 增长提醒阈值默认 `100M`，支持 `100M`、`1G`、字节数，以及按速度设置的 `100M/d`（平均每天增长 100M）、`1M/s`（平均每秒增长 1M）。
- 扫描进度先建立条目基线并显示百分比；增长提醒按变化量从小到大呈现，并隐藏已被超阈值子目录覆盖的父目录。
- 交互式结果先展示当前占用重点路径，最后固定输出增长提醒。
- 无参模式结束后提示“按任意键退出”，适合直接双击 exe 使用；带参数调用不暂停。
- 识别符号链接、目录联接点等 Windows Reparse Point，默认不跟随，避免重复计数。
- 按 NTFS 文件记录（file record）去重：硬链接共享的同一份数据只计一次占用。
- 占用量取自文件系统的簇分配量（`AllocationSize`），不是逻辑长度：稀疏文件与云端占位文件按实际占用的簇计（可为 0），不再把整份逻辑大小当成占用。
- 区分三个口径：表面大小（逻辑长度之和）、占用（去重后的物理占用）、可回收（删掉该路径真正能还给卷的空间）。
- 打不开的文件（分页文件、休眠文件、受保护目录里的文件）不会凭空消失：改用目录列表里的长度计入，占用标为估算（输出中标注 `[allocation estimated]`）。
- 有参扫描与交互式进度基线使用 Rayon 受控并行；默认线程数不超过 8，可用 `RAYON_NUM_THREADS` 覆盖。
- 有参模式提供稳定的 CLI 和 JSON 输出，便于 Agent、脚本和自动化任务调用。
- 只读设计：不删除、不移动、不创建符号链接。

## 构建

需要 Rust stable：

```powershell
cargo build --release
```

可执行文件位于 `target\release\space_tracker.exe`。压缩快照使用 Rust 的 zstd crate；它不要求安装 .NET Desktop Runtime。

## 人类使用

直接运行：

```powershell
.\target\release\space_tracker.exe
```

依次输入：

```text
扫描路径             [默认 C:\]
数据存放路径         [默认 exe 所在目录]
增长提示阈值         [默认 100M；也可输入 100M/d、1M/s]
```

直接回车接受默认值。程序会在数据存放路径下创建 `space-tracker` 子目录，再按扫描根目录分开保存快照。第二次扫描同一路径后，程序会显示两次快照之间的时间段、超过阈值的增长目录和增长大小。

无参模式结束时会等待按下任意键再退出，避免直接双击 exe 时窗口立即关闭；从命令行带参数调用时保持原有 CLI 行为。

## Agent / CLI 使用

带参数时不会进入交互模式：

```powershell
$tool = ".\target\release\space_tracker.exe"
$store = "D:\space-tracker-snapshots"
$root = "C:\Users\YourName\AppData"

& $tool scan $root --store $store --compact --json
& $tool history --root $root --store $store --json
& $tool delta --root $root --store $store --min-bytes 100M/d --json
& $tool children --root $root --path . --store $store --json
& $tool query --root $root --path AppData --store $store --limit 50 --json
& $tool links --root $root --store $store --json
& $tool reclaim --root $root --path AppData --store $store --json
& $tool audit --root $root --store $store --json
```

命令说明：

- `scan`：扫描并保存压缩快照；默认不跟随 Reparse Point。`--compact` 保留用于兼容旧调用，新格式始终使用 zstd 压缩。
- `history`：只读取 manifest 摘要，列出同一存储目录中的历史快照。
- `delta`：比较同一根目录的两次快照，输出增长/缩小目录、新增文件和删除文件；`--min-bytes` 支持绝对大小，也支持 `大小/时间单位` 形式，按两次快照的间隔换算本次实际阈值。
- `children`：查看指定目录的直接子目录和文件。
- `query`：面向 `.base.zst`/`.delta.zst` 的显式查询入口，按路径列出直接子项；`children` 继续作为兼容命令保留。
- `links`：列出识别到的 Reparse Point、目标路径和未跟随状态。
- `reclaim`：报告删除某个路径真正能还给卷的空间，并给出它的表面大小、占用、共享量与硬链接数。
- `audit`：核对一次快照的计数口径：文件记录数、链接数分布、占位文件与稀疏文件带来的表观大小差、疑似重复副本，以及扫描到的卷序列号。

## 三个口径

一次扫描会同时给出三个数，它们回答的是不同问题，不能互相替代：

| 口径 | 含义 | 回答的问题 |
| --- | --- | --- |
| 表面大小（`size`） | 所有可见路径的逻辑长度之和 | 这些文件“看起来”有多大 |
| 占用（`allocated`） | 按文件记录去重后的簇分配量 | 盘上真的被它们占了多少 |
| 可回收（`reclaimable`） | 删除该路径真正能还给卷的字节 | 我删掉它能腾出多少空间 |

三条规则决定了这些数字：

1. **硬链接只算一次占用。** 两个目录项指向同一份文件记录时，它们是同一份数据。占用按“归属路径”（同一记录中最小的那个路径）计一次，因此父目录的占用等于子目录占用之和。
2. **稀疏文件与云端占位文件按实际簇数计。** OneDrive 的按需文件在本地没有数据，只有逻辑长度；NTFS 报告的簇分配量对它们是 0。这类文件的表观大小计入表面大小，占用为 0，删除也换不回空间。输出中会标注 `[placeholder]` 与 `[sparse]`。
3. **可回收量看“所有链接是否都在这一侧”。** 一份被两个兄弟目录引用的数据，删掉其中任何一个都腾不出空间——记录还活着；只有同时包含全部链接的那个目录（以及它的上级）才算数。因此可回收量不是子目录之和，而是记在最近的那个共同祖先上。链接不在扫描树内的记录（例如同样存在于回收站）永远不计入可回收量。

`shared` 字段标出“本目录里、但归属在别处”的副本大小：这些字节看起来在这里，删掉却换不回来。

## 打不开的文件

分页文件、休眠文件，以及受保护目录（回收站、`System Volume Information`、`WindowsApps`）里的文件，任何进程都打不开——打不开就没有句柄，也就读不到簇分配量。如果就此跳过，它们会从计量里凭空消失：本机 F: 卷的分页文件一个就有 26 GiB。

这类文件的名字仍然列在目录里，目录列表带着它的逻辑长度。工具因此在打不开文件时退回列表：

- 表面大小照常计入（来自目录列表）。
- 占用按逻辑长度**估算**，并在条目上标注 `[allocation estimated]`；`audit` 会单独报出这类文件的数量与合计。
- 列表若标明文件是稀疏、压缩或重解析点（云端占位文件），它拥有的簇少于逻辑长度，就不按长度估算，避免把卷的占用算多。

这是估算而不是测量：文件系统没有说过它拥有多少簇。簇对齐的零头没有计入。

## 快照存储格式

指定 `--store D:\space-tracker-data` 后，实际数据位于：

```text
D:\space-tracker-data\space-tracker\<root-fingerprint>\
├── manifest.json
├── snapshot-<time>.base.zst
└── snapshot-<time>.delta.zst
```

同一根目录的第一次扫描写一个完整 `.base.zst`；后续扫描只保存新增、删除和发生字段变化的条目到 `.delta.zst`。查询时按基线叠加增量恢复目标时刻的逻辑快照。基线和增量载荷沿用 Rust 当前 `Snapshot`/`Entry` 数据结构，只是使用 zstd 压缩；这样可以先消除重复完整快照的磁盘开销，并为后续索引化二进制载荷保留兼容边界。

为避免长期运行后增量链无限变长，连续 32 个 delta 后下一次扫描会自动建立新的 base；旧文件不会被自动删除。

旧版 `.json` 快照仍可读取。若存储目录中只有旧格式，下一次新扫描会建立新的 `.base.zst`，不会删除旧 JSON。

## 隐私与快照

快照可能包含扫描根路径、链接目标和无法访问的文件路径，因此默认只应保存在自己的机器上，不要直接上传快照。仓库已经通过 `.gitignore` 排除快照、验证目录和构建产物；公开文档只使用通用路径示例，不包含开发机用户名或本地工程路径。

## 当前边界

占用口径现在按 NTFS 文件记录去重，取文件系统的簇分配量，因此硬链接、稀疏文件和云端占位文件都不再被当成“删掉就能释放”的空间。仍然存在的边界：

- Reparse Point（符号链接、目录联接点、挂载点）只记录、不跟随，因此联接点目标的内容不计入本次扫描。链接关系可用 `links` 命令单独查看。
- 无权限读取的目录（例如回收站、`System Volume Information`）会以错误形式保存在快照里，其中的文件不计入任何口径。
- 打不开的单个文件按目录列表里的长度计入，占用为估算值（见「打不开的文件」）。
- 表面大小仍然按可见路径相加，同一份数据经多个路径可见时会在这一项里重复出现；要判断“删了能腾多少”，看可回收量。
- 不执行迁移、建链和删除操作：所有统计只读。
