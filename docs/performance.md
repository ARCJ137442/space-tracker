# 性能测试与优化记录

这份文档记录 MVP 在一台 Windows 开发机上的匿名化参考结果。数字用于说明量级和优化方向，不代表所有机器的固定性能；公开仓库不保存原始快照或本机绝对路径。

## 测试范围

- 扫描根目录：`C:\`
- 扫描方式：Release 构建，默认不跟随 Windows Reparse Point
- 快照位置：扫描根目录之外的独立数据目录
- `duration_ms`：目录遍历阶段耗时
- 端到端时间：包含快照保存阶段
- 扫描只读，不删除、移动或修改扫描目录

## 参考结果

| 版本/格式 | 文件 | 目录 | Reparse | 错误 | 逻辑大小 | 遍历耗时 | 端到端耗时 | 快照大小 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 基线：内存缓冲 + 可读 JSON | 971,727 | 185,979 | 384 | 124 | 141,217,892,357 B | 57,655 ms | 未单独记录 | 382,452,961 B |
| 优化：流式写入 + 紧凑 JSON，热缓存第 1 次 | 971,967 | 185,981 | 384 | 124 | 141,212,354,239 B | 32,866 ms | 33,410 ms | 306,098,765 B |
| 优化：流式写入 + 紧凑 JSON，热缓存第 2 次 | 971,972 | 185,981 | 384 | 124 | 141,230,618,611 B | 32,949 ms | 33,472 ms | 306,099,843 B |
| 优化：流式写入 + 可读 JSON | 971,969 | 185,982 | 384 | 124 | 141,243,288,192 B | 32,303 ms | 32,961 ms | 382,527,473 B |

基线是第一次全盘扫描，优化版紧接着运行，操作系统文件缓存状态不同，因此不能把全部时间差归因于代码。两次优化版热缓存复测只相差 83 ms，说明该版本在这组数据上稳定在约 33 秒量级。

同一优化版本下，紧凑快照比可读快照减少约 19.98%。流式读写不再通过 `serde_json::to_vec_pretty` 创建整份临时字节数组，读取时也使用 `BufReader` 直接反序列化，从而降低大快照的额外内存压力。

## 增量压缩格式复测

在同一类 Windows 开发环境使用 Release 构建重新扫描 `C:\`，新格式结果如下：

| 项目 | 结果 |
|---|---:|
| 文件 / 目录 | 597,119 / 145,021 |
| Reparse Point / 错误 | 395 / 125 |
| 首次遍历耗时 | 67,537 ms |
| `.base.zst` | 11,566,963 B |
| 第二次 `.delta.zst` | 6,769 B |
| 第二次扫描的时间间隔 | 80,336 ms |
| `delta` 查询耗时 | 约 9.2 s |
| `query` 子目录查询耗时 | 约 4.8 s |

首次基线的压缩结果已经从约 300MB 量级降到约 11.6MB；后续扫描只保存变化条目，没有再次写入完整快照。`history` 读取 manifest 摘要，不需要解压基线。当前 `delta`/`query` 为兼容既有 `Snapshot` 结构，会恢复完整基线后再叠加增量，所以查询时间仍是下一阶段的优化重点。

## 扫描热路径与并行复测

扫描器现在按使用方式分为两条路径：

- 有参 CLI 使用 Rayon 递归处理宽目录：每个分区维护局部条目、错误和计数，最后归并为同一个 `Snapshot`，不跟随 Reparse Point。
- 交互式 CLI 的进度基线也使用同一线程池；正式扫描保留顺序遍历，以便稳定更新 `FnMut` 进度回调。
- 并行任务只在目录条目数达到阈值时创建，避免为大量小目录重复支付调度成本；默认线程数为 `min(逻辑处理器数, 8)`，也可通过 `RAYON_NUM_THREADS` 覆盖。

受控递归并行版本在同一台机器上做了线程数探查：单线程约 21.4 秒，4 线程约 8.1 秒，8 线程约 6.6 秒；16 线程的一轮探查反而回升到约 15.2 秒。另一次不设置覆盖变量的默认扫描约 11.4 秒。文件系统缓存、实时防护、扫描期间的文件变化和权限错误会显著影响结果，因此这些数字用于证明调度方向和线程上限选择，不代表所有机器的固定加速比。

交互式 C 盘复测中，新的并行进度基线统计了约 808,241 个条目，耗时约 6.6 秒；正式扫描耗时约 23.9 秒。百分比提升了可追踪性，正式扫描仍保留顺序回调以保证输出稳定；有参 CLI 不执行进度基线，以保留最快扫描路径。

## 已实施的优化

1. 使用 `BufWriter + serde_json::to_writer[_pretty]` 保存快照。
2. 使用 `BufReader + serde_json::from_reader` 读取快照。
3. 增加 `scan --compact`，适合接近百万文件的大盘扫描。
4. Reparse Point 目标只解析一次，避免重复调用 `canonicalize`。
5. 使用 zstd 流保存 `.base.zst` 和 `.delta.zst`；后续扫描只编码发生变化的条目。
6. 使用 manifest 保存摘要，使 `history` 不必读取百万条目快照。
7. 使用 Rayon 对宽目录递归拆分，局部结果 `fold/reduce` 归并，避免共享状态锁和每个文件一个结果对象。
8. 默认限制扫描线程数为最多 8，并允许 `RAYON_NUM_THREADS` 针对具体磁盘和机器调参。
9. 扫描热路径直接维护规范化相对路径字符串，并在没有进度回调时跳过进度计时。

## 验证重点

参考扫描中，工具能够同时提供：

- 当前占用：`C:\Users`、`C:\Windows`、`C:\Program Files` 等顶层目录。
- 用户数据下钻：`C:\Users\YourName\AppData\Local`、`Roaming` 和 `LocalLow`。
- 增长定位：从根目录一路下钻到应用缓存目录和具体新增文件。
- 链接识别：`C:\Users\All Users -> C:\ProgramData` 被标记为未跟随，不重复计数。

## 结论与边界

- 当前主要成本是 Windows 文件系统元数据遍历和内存中的条目集合，而不是 JSON 写入本身。
- 并行扫描已经进入有参 CLI 和交互式进度基线；正式交互扫描仍是顺序回调路径。若继续压缩扫描时间，应继续验证权限错误、联接点、动态变化文件以及不同存储介质上的线程数上限。
- 逻辑文件大小不等于 NTFS 实际占用；错误数应作为扫描完整度指标。
- 原始快照属于本地数据，不应提交到公开仓库；仓库的 `.gitignore` 已排除快照和验证产物。
- 如果未来主要操作从“增长比较”转为高频随机查询，应在不改变 `.base.zst`/`.delta.zst` 文件契约的前提下，引入版本化二进制记录和目录索引；不能仅靠继续提高压缩级别解决解码成本。
